A vector index ranks node or edge embeddings by distance to a query vector. Use it for
semantic search, recommendations, and retrieval over any label that stores an
embedding as a top-level numeric array property.

Every definition declares a non-zero dimension and one distance metric: cosine,
Euclidean, or Manhattan. Stored embeddings and every query vector must have exactly
the declared dimension.

For background, see [What is vector search?](/learn/vector-search/what-is-vector-search)
and [vector distance metrics](/learn/vector-search/vector-distance-metrics).

Vector search and vector index management are native-only: Cypher and SQL have no
syntax for them. The [Cypher guide](/database/helix-db/query-guides/cypher#what-is-not-supported)
lists what Cypher covers.

## Create a vector index

<CodeGroup>

```rust Rust
write_batch()
    .var_as(
        "index",
        g().create_vector_index_nodes(
            "Doc",
            "embedding",
            std::num::NonZeroUsize::new(3).expect("non-zero dimension"),
            VectorDistanceMetric::Cosine,
            None::<&str>,
        ),
    )
    .returning(["index"]);
```

```ts TypeScript
writeBatch()
  .varAs(
    "index",
    g().createVectorIndexNodes(
      "Doc",
      "embedding",
      3,
      VectorDistanceMetric.Cosine,
      null,
    ),
  )
  .returning(["index"]);
```

```

  "query_name": "create_doc_vector_index",
  "query": {
    "write": {
      "entries": [{
        "query": {
          "name": "index",
          "root": {
            "create_index": {
              "spec": {
                "node_vector": {
                  "label": "Doc",
                  "property": "embedding",
                  "dimension": 3,
                  "metric": "cosine"
                }
              },
              "if_not_exists": true
            }
          }
        }
      }],
      "returns": ["index"]
    }
  }
}
```

</CodeGroup>

Pass a tenant property as the final argument to partition the index by tenant. Any
property name works. A record without the tenant property is not indexed. See
[tenant-partitioned search indexes](/database/helix-cloud/operate/multi-tenancy#tenant-partitioned-search-indexes).

Creation returns a receipt before the backfill over existing data finishes. The index
becomes queryable only after validation and atomic activation. Until then, searching it
fails with `index_not_found`, as for a missing index.

## Stored vectors

An indexed property accepts `f32`, `f64`, or `i64` arrays, or a generic array of
numbers, converted to `f32`. A record without the property is not indexed. A write fails
when the property holds:

| Value | Error |
| --- | --- |
| A different number of components than the index dimension | `invalid_vector_dimension` |
| `NaN`, infinity, or an `f64` too large for `f32` | `invalid_vector_component` |
| All zeros, in a cosine index | `zero_norm_cosine_vector` |
| A component large enough to overflow the Euclidean or Manhattan distance | `vector_component_magnitude_exceeded` |
| Any other type, including `null` | `invalid_query` |

Existing records with such values block a build instead; see
[Troubleshoot index operations](/database/helix-db/query-guides/troubleshooting#index-operation-is-blocked).
An empty query vector, or one with `NaN` or infinite components, fails with
`invalid_search_input` as a literal and `invalid_query` as a parameter.

## Search an index

Search the whole index when every record of the label is a valid result. This request
returns the ten `Doc` nodes closest to the query vector:

<CodeGroup>

```rust Rust
read_batch()
    .var_as(
        "hits",
        g().vector_search_nodes("Doc", "embedding", vec![0.1, 0.8, 0.2], 10, None)
            .value_map(Some(vec!["$id", "title", "$distance"])),
    )
    .returning(["hits"]);
```

```ts TypeScript
readBatch()
  .varAs(
    "hits",
    g()
      .vectorSearchNodes("Doc", "embedding", [0.1, 0.8, 0.2], 10, null)
      .valueMap(["$id", "title", "$distance"]),
  )
  .returning(["hits"]);
```

```go Go
helix.ReadQuery("similar_docs").
	VarAs(
		"hits",
		helix.G().
			VectorSearchNodes("Doc", "embedding", []float32{0.1, 0.8, 0.2}, 10).
			ValueMap("$id", "title", "$distance"),
	).
	Returning("hits")
```

```python Python
(

        "hits",
        g()
        .vector_search_nodes("Doc", "embedding", [0.1, 0.8, 0.2], 10)

    )
    .returning(["hits"])

```

```json JSON
{
  "request_type": "read",
  "query_name": "similar_docs",
  "query": {
    "read": {
      "entries": [{
        "query": {
          "name": "hits",
          "root": {
            "value_map": {
              "input": {
                "vector_search_nodes": {
                  "label": "Doc",
                  "property": "embedding",
                  "query_vector": { "value": { "f32_array": [0.1, 0.8, 0.2] } },
                  "k": { "literal": 10 }
                }
              },
              "properties": ["$id", "title", "$distance"]
            }
          }
        }
      }],
      "returns": ["hits"]
    }
  }
}
```

</CodeGroup>

Hits arrive closest first, ordered by `$distance` and then by ID. Use
`vectorSearchEdges` / `vector_search_edges` (`VectorSearchEdges` in Go) to search an
edge index. For a tenant-partitioned index, pass the tenant value as the final
argument.

`$distance` exists only on the hit stream: a step to another element drops it, and a
projection ends the traversal. To keep it, `bind` the hit and read it with
`projectBindings`; see
[Keep search scores after traversing](/database/helix-db/query-guides/projections#keep-search-scores-after-traversing).

`k` must be at least 1: a literal `0` fails with `invalid_search_result_count`, and a
parameter `k` of `0` or less fails with `invalid_query`.

## Distance values

`$distance` is lower for closer vectors under every metric:

| Metric | `$distance` | Range |
| --- | --- | --- |
| Cosine | `(1 - cosine similarity) / 2` | `0` (same direction) to `1` (opposite) |
| Euclidean | Squared Euclidean distance, with no square root | `0` and up |
| Manhattan | Sum of absolute component differences | `0` and up |

Straight-line distance is the square root of a Euclidean `$distance`; cosine similarity
is `1 - 2 × $distance`.

## Index structure

Vector indexes are HNSW graphs with fixed settings: `m` 16 (32 on the bottom layer),
`ef_construction` 200, and a search `ef` of `max(k, 100)`. Queries cannot change them.
Results are approximate, so a whole-index search can miss a true nearest neighbor.

Each insert searches the bottom layer from the nearest nodes it finds one layer up, so
vectors where two clusters meet stay linked to both. Indexes built by earlier releases
could leave the bottom layer split between well-separated clusters, so that a small share
of rows (about 0.5% of SIFT 1M) was not found even by its own vector. Drop and create such
an index again to rebuild it with the better-connected graph.

## Prefilter with a traversal

To rank only the nodes or edges a traversal reaches, such as documents a user may
access, search within the traversal instead of the whole index. See
[Prefiltered search](/database/helix-db/query-guides/prefiltering#vector-prefiltering).

Prefilter when only some records are valid answers: filtering whole-index hits
afterwards can leave fewer than `k`. Prefiltering also
[ranks a small candidate set exactly](/database/helix-db/query-guides/prefiltering#how-it-works).

## Combine vector and text search

HelixDB has no operator that fuses vector and BM25 rankings. Run both searches in one
read batch (one snapshot) and merge the ranked lists in your application, for example
with reciprocal rank fusion:

<CodeGroup>

```rust Rust
read_batch()
    .var_as(
        "semantic",
        g().vector_search_nodes("Doc", "embedding", vec![0.1, 0.8, 0.2], 20, None)
            .value_map(Some(vec!["$id", "$distance"])),
    )
    .var_as(
        "keyword",
        g().text_search_nodes("Doc", "body", "consensus protocol", 20, None)
            .value_map(Some(vec!["$id", "$score"])),
    )
    .returning(["semantic", "keyword"]);
```

```ts TypeScript
readBatch()
  .varAs(
    "semantic",
    g()
      .vectorSearchNodes("Doc", "embedding", [0.1, 0.8, 0.2], 20, null)
      .valueMap(["$id", "$distance"]),
  )
  .varAs(
    "keyword",
    g()
      .textSearchNodes("Doc", "body", "consensus protocol", 20, null)
      .valueMap(["$id", "$score"]),
  )
  .returning(["semantic", "keyword"]);
```

## Search consistency

By default, searches include committed writes that the index worker has not published
into the index yet. A read request can opt into `eventual` search, which bounds that
work per search. See [Search consistency](/database/helix-db/query-guides/search-consistency)
for both modes, searches in write batches, and `index_backpressure`.

## Result limits

The server caps the effective result count of a whole-index search at 800. A narrower
bound from the surrounding plan can lower it. Prefiltered searches have their own
[limits](/database/helix-db/query-guides/prefiltering#result-limits).

## Operational notes

- Creation returns before the backfill necessarily finishes.
- Writes made while an index builds are queued and published after it activates;
  strong searches include them as soon as the index is active. Until then they count
  toward [index backpressure](/database/helix-db/query-guides/search-consistency#index-backpressure).
- A new generation remains hidden until validation and activation succeed.
- Dropping an index is also a durable lifecycle operation.

### How an index is built

A vector index is built one vector at a time unless in-memory builds are turned on with
[`HELIX_VECTOR_BULK_BUILD_MEMORY_BYTES`](/database/helix-db/start-here/local-development/local-server#run-with-seaweedfs-persistence).
With them on, an index without a tenant property is built in memory when its label's
vectors fit the memory they are given: the whole graph is linked on every core and
written once, many times faster. An index that does not fit, and every
tenant-partitioned index, is still built serially. The
[operation status](/database/helix-db/query-guides/secondary-indexes#track-an-index-operation)
of a vector build says which, in `vector_build_path`:

| `vector_build_path` | Meaning |
| --- | --- |
| `{"path": "bulk"}` | Built in memory. Reported by every server for as long as the build is at stage `scan`, and afterwards by the server that built it |
| `{"path": "serial", "reason": "..."}` | Built one vector at a time. Reported only by the server running the build, until it restarts |
| absent | Not a vector build, not decided yet, or this server did not decide |

`reason` is `bulk_builds_disabled`, `over_memory_budget`, `too_few_vectors` (fewer than
4,096), `tenant_partitioned`, `earlier_attempts_failed`, `bulk_attempt_failed`,
`too_many_rows_changed`, or `resumed_serial_scan`.

While a build is on the in-memory path its status also carries `vector_bulk_build`,
with which attempt it is (`bulk_attempt` of `bulk_attempt_limit`, reported by every
server; not the operation's own `attempt`, which counts retried steps) and, from the
server running it, what it is doing:

| `phase` | Other fields | Meaning |
| --- | --- | --- |
| `waiting` | `waiting_for`: `turn` or `memory` | Not started. Another build reads or links (one does at a time), or running in-memory builds hold the memory this one needs. A waiting build does not slow other index operations |
| `reading` | `members_read`, `members` | Reading the label's source rows into memory |
| `linking` | `vectors_linked`, `vectors` | Linking the graph |
| `writing` | `nodes_written`, `nodes`, `paused_for_write_buffer` | Writing the graph. The `progress` counters of the operation move only in this phase |
| `discarding` | `rows_deleted` | Deleting what an attempt that did not finish wrote, before the next one starts |

A restart during the build discards what was written and starts the next attempt, and
the counters start again from zero. Every attempt counts that a kill, a crash, a stop
or a deploy ended. After three, the build continues serially
(`earlier_attempts_failed`). A build that blocks returns to the serial stage first, so
its retry starts at attempt one. An attempt that fails in a way a serial build cannot
is not tried again: what it wrote is deleted and the index is built serially at once
(`bulk_attempt_failed`).

Rows written while an index is built in memory are indexed after the build, like any
write, and each one that changes after the build read it is first taken out of the
in-memory graph, which costs far more than writing a row that did not change. A build
that finds more than about an eighth of its rows changed stops its in-memory attempt,
deletes what it wrote and builds the index serially at once
(`too_many_rows_changed`): finishing in memory would take longer.

<Warning>
  Turn in-memory builds on only once every server that can become the writer runs a
  release that has them. A release from before them (Docker v0.0.18 and earlier) cannot
  open a database as its writer while any build reports stage `scan` with path `bulk`:
  it stops at startup, and by trying it takes the writer role from the running server,
  which then fails every request until it is restarted.

  Before rolling back to such a release during an in-memory build, let the build finish,
  or restart the current release with `HELIX_VECTOR_BULK_BUILD_MEMORY_BYTES` unset and
  wait until the build no longer reports path `bulk` (it deletes what it wrote, at about
  2,600 entities a second, and continues serially under either release), or abort it and
  wait until it reports `aborted`. A status reports `bulk` for as long as that is what a
  restart would find.

  That makes a database readable by such a release only while its index storage version
  is below 8, where an abort deletes the same rows far more slowly. The current release
  moves a database it opens as the writer to version 8: an abort then ends within
  seconds and leaves the rows to compactions, and no release from before in-memory
  builds opens the database, so going back past it needs a backup taken before the
  upgrade.
</Warning>
