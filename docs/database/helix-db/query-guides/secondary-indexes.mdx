Secondary indexes narrow node or edge sources by property. Index creation is
asynchronous and includes existing data through a durable backfill.

## Index families

| Family | Entities | Use |
| --- | --- | --- |
| Equality | Nodes and edges | `eq` and `isIn` matches |
| Unique equality | Nodes only | Equality matches, plus at most one node per value |
| Range, ascending or descending | Nodes and edges | `gt`, `gte`, `lt`, `lte`, and `between` comparisons, and sorted reads |

A definition names the entity kind, label, and property, plus `unique` (node equality
only) or the range direction. A label and property can hold one equality index and one
range index, but not both range directions.

## Create an equality index

<CodeGroup>

```rust Rust
write_batch()
    .var_as(
        "index",
        g().create_index_if_not_exists(IndexSpec::node_equality("User", "status")),
    )
    .returning(["index"]);
```

```ts TypeScript
writeBatch()
  .varAs(
    "index",
    g().createIndexIfNotExists(IndexSpec.nodeEquality("User", "status")),
  )
  .returning(["index"]);
```

```go Go
helix.WriteQuery("create_user_status_index").
	VarAs(
		"index",
		helix.G().CreateIndexIfNotExists(
			helix.NodeEqualityIndex("User", "status"),
		),
	).
	Returning("index")
```

```python Python
(
    write_batch()
    .var_as(
        "index",
        g().create_index_if_not_exists(
            IndexSpec.node_equality("User", "status")
        ),
    )
    .returning(["index"])
)
```

```json JSON
{
  "request_type": "write",
  "query_name": "create_user_status_index",
  "query": {
    "write": {
      "entries": [{
        "query": {
          "name": "index",
          "root": {
            "create_index": {
              "spec": {
                "node_equality": {
                  "label": "User",
                  "property": "status",
                  "unique": false
                }
              },
              "if_not_exists": true
            }
          }
        }
      }],
      "returns": ["index"]
    }
  }
}
```

</CodeGroup>

The returned DDL receipt identifies the durable operation. A build is not listed as an
active index until it succeeds, so poll its `operation_id` before depending on indexed
performance.

## Track an index operation

<CodeGroup>

```rust Rust
read_batch()
    .var_as("status", g().get_index_operation(operation_id))
    .returning(["status"]);
```

```ts TypeScript
readBatch()
  .varAs("status", g().getIndexOperation(operationId))
  .returning(["status"]);
```

```go Go
helix.ReadQuery("index_operation").
	VarAs("status", helix.G().GetIndexOperation(operationID)).
	Returning("status")
```

```python Python
(
    read_batch()
    .var_as("status", g().get_index_operation(operation_id))
    .returning(["status"])
)
```

```json JSON
{
  "request_type": "read",
  "query": {
    "read": {
      "entries": [{
        "query": {
          "name": "status",
          "root": { "get_index_operation": { "operation_id": "<operation_id>" } }
        }
      }],
      "returns": ["status"]
    }
  }
}
```

</CodeGroup>

`status` is `queued`, `running`, `blocked`, `succeeded`, or `aborted`. A `blocked`
operation carries a `blocker_code` and does not resume on its own. Fix the cause, then
run `retry_index_operation` (`retryIndexOperation`) as a write with the same
`operation_id`, or `abort_index_operation` (`abortIndexOperation`) to discard the build.

Repeating the same CREATE:

| Existing index | Result |
| --- | --- |
| Building | `existing_operation` with the same `operation_id` |
| Active | `already_active`, no `operation_id` |
| Aborted or dropped | A new build with a new `operation_id` |
| Still aborting or dropping | Fails with `index_busy`; retry once that finishes |
| Building or active with a different `unique` flag or range direction | Fails with `index_definition_conflict`; drop it first |

The two failures apply even with `createIndexIfNotExists`.

## Which predicates use an index

Only a label-scoped source reads an index:
`nWithLabelWhere("User", SourcePredicate.eq("status", "active"))` (or the
language-equivalent builder), or a `.where(...)` directly after `nWithLabel("User")`. A
source predicate without a label scans every node.

| Predicate | Index |
| --- | --- |
| `eq`, `isIn` with a literal list or a parameter, `compare` with `Eq` | Equality, or for literal values a range index when the property has no equality index |
| `gt`, `gte`, `lt`, `lte`, `between` with a literal or parameter bound | Range |
| `neq`, `not`, `startsWith`, `endsWith`, `contains`, `isNull`, `hasKey` | Never (scanned) |
| A comparison between two properties | Never |

- `and` intersects the index reads of its indexable parts and tests the rest row by row.
- `or` uses indexes only when every branch is indexable, and only one `or` per `and`.
- A range index also serves `orderBy` without sorting; see
  [Ordering and pagination](/database/helix-db/query-guides/ordering-and-pagination#sorting-cost).
- A `.where(...)` after a traversal step, such as `out("FOLLOWS")`, with `eq` or `isIn`
  on an equality-indexed node property reads the matching IDs from the index once per
  request and checks each streamed node against them. Range predicates and
  `eq(property, null)` there are tested row by row.

Cypher and [SQL](/database/helix-db/query-guides/sql#indexes-and-performance)
statements use these indexes automatically, without naming them. An equality or
`IN` match on a labeled node reads an equality index, and range comparisons and
ordered `LIMIT` reads use a range index:

```cypher
// parameters: {"status": "active"}
MATCH (u:User {status: $status})
RETURN u.name AS name
```

Explain the statement to see which index the plan reads. See
[Cypher indexes and performance](/database/helix-db/query-guides/cypher#indexes-and-performance)
for the conditions that keep an index in use.

On a server, `GET /v2/diagnostics` lists recent queries that need an index
(`queries.missing_indexes`) and unbounded scans (`queries.unbounded_scans`).

## Range indexes

Create an ascending range index on `Post.created_at`:

<CodeGroup>

```rust Rust
write_batch()
    .var_as(
        "index",
        g().create_index_if_not_exists(IndexSpec::node_range("Post", "created_at")),
    )
    .returning(["index"]);
```

```ts TypeScript
writeBatch()
  .varAs(
    "index",
    g().createIndexIfNotExists(IndexSpec.nodeRange("Post", "created_at")),
  )
  .returning(["index"]);
```

```go Go
helix.WriteQuery("create_post_created_at_index").
	VarAs(
		"index",
		helix.G().CreateIndexIfNotExists(
			helix.NodeRangeIndex("Post", "created_at"),
		),
	).
	Returning("index")
```

```python Python
(
    write_batch()
    .var_as(
        "index",
        g().create_index_if_not_exists(
            IndexSpec.node_range("Post", "created_at")
        ),
    )
    .returning(["index"])
)
```

```json JSON
{
  "request_type": "write",
  "query_name": "create_post_created_at_index",
  "query": {
    "write": {
      "entries": [{
        "query": {
          "name": "index",
          "root": {
            "create_index": {
              "spec": {
                "node_range": {
                  "label": "Post",
                  "property": "created_at",
                  "direction": "asc"
                }
              },
              "if_not_exists": true
            }
          }
        }
      }],
      "returns": ["index"]
    }
  }
}
```

</CodeGroup>

Use `nodeRangeDesc` / `node_range_desc` (`NodeRangeDescIndex` in Go) for a descending
index, and `edgeRange` / `edge_range` (`EdgeRangeIndex`) for edges. Native queries read
an ascending index backwards for a descending sort; Cypher and SQL read only in the
index's direction, so match their `ORDER BY`.

## Indexed values

| Index | Indexed | Not indexed | Rejected |
| --- | --- | --- | --- |
| Equality | Booleans, numbers, date-times, strings, bytes, and typed arrays | A missing property, `null`, and `NaN` | Generic arrays and objects |
| Range | Numbers, date-times, and strings | A missing property | `null`, booleans, bytes, arrays, objects, and `NaN` |

Numbers sort before date-times, and date-times before strings. A rejected value fails the
write, and existing rows holding one block a build. `eq(property, null)` scans the label.

## Unique indexes

Create one with `nodeUniqueEquality` / `node_unique_equality`
(`NodeUniqueEqualityIndex` in Go). Any number of nodes may have the property missing,
`null`, or `NaN`, since those are not indexed.

A unique index checks writes from the moment its build starts: a write that would
duplicate a value the index already holds fails with `unique_constraint_violation`,
before and after the index activates. A duplicate of a row the backfill has not reached
yet is not visible to that check, so the backfill becomes blocked when it reaches the
pair, as it does if existing data contains duplicates. Writes stay checked while it is
blocked; fix the source data, then retry the same operation instead of creating a new
definition.
