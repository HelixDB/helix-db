Traversal operations consume the current stream and produce the next stream.

| Operation | Result |
| --- | --- |
| `out(label)` | Destination nodes of outgoing edges |
| `in(label)` | Source nodes of incoming edges |
| `both(label)` | Adjacent nodes in either direction |
| `outE(label)` / `inE(label)` / `bothE(label)` | The outgoing, incoming, or all edges themselves |
| `outN()` | From an edge to its target node |
| `inN()` | From an edge to its source node |
| `otherN()` | From an edge to the endpoint the traversal did not come from |
| `dedup()` | Remove duplicate results, keeping the first |

The label is optional. Rust takes `Some("FOLLOWS")` or `None`, and the Rust and Python
incoming step is `in_`.

These steps work with named results, paths, and per-row values:

| Operation | Result |
| --- | --- |
| `as(name)` / `store(name)` | Save the current stream under `name` and pass it on unchanged (`as_` in Rust and Python) |
| `select(name)` | Replace the current stream with the stream saved under `name` |
| `inject(name)` | Append the stream saved under `name` to the current stream, or start from it |
| `bind(name)` | Keep the current element on each row; see below |
| `path()` | Return each row's path of visited elements with the row |
| `simplePath()` | Drop rows whose path visits an element twice |
| `withSack(value)`, `sackSet(property)`, `sackAdd(property)`, `sackGet()` | Start a per-row value, set it from a property, add a numeric property to it, and return it with the row |
| `fold()` / `unfold()` | Collect the stream into one value, and expand it back into rows |

Rows that carry a visible path or sack return
`{"current": ..., "bindings": ..., "path": ..., "sack": ...}` instead of `{"$id": ...}`
when the entry ends without a projection.

## Follow a named result

<CodeGroup>

```rust Rust
read_batch()
    .var_as(
        "user",
        g().n_where(SourcePredicate::eq("username", "alice")),
    )
    .var_as(
        "friends",
        g()
            .n(NodeRef::var("user"))
            .out(Some("FOLLOWS"))
            .dedup()
            .limit(25)
            .value_map(Some(vec!["$id", "username"])),
    )
    .returning(["friends"]);
```

```ts TypeScript

  .returning(["friends"]);
```

## Preserve correlated values

A traversal normally forgets where it has been: after `out(...)`, each row holds only
the node it reached. Use `bind` to name a point in the traversal so each result row
keeps a value from it. This request returns one row per service and the workload it
routes to:

<CodeGroup>

```rust Rust
read_batch()
    .var_as(
        "routes",
        g()
            .n_with_label("Service")
            .bind("service")
            .out(Some("ROUTES_TO"))
            .project_bindings(vec![
                BindingProjection::binding("service", "name", "service"),
                BindingProjection::current("name", "workload"),
            ]),
    )
    .returning(["routes"]);
```

```ts TypeScript
readBatch()
  .varAs(
    "routes",
    g()
      .nWithLabel("Service")
      .bind("service")
      .out("ROUTES_TO")
      .projectBindings([
        BindingProjection.binding("service", "name", "service"),
        BindingProjection.current("name", "workload"),
      ]),
  )
  .returning(["routes"]);
```

```go Go
helix.ReadQuery("service_routes").
	VarAs(
		"routes",
		helix.G().
			NWithLabel("Service").
			Bind("service").
			Out("ROUTES_TO").
			ProjectBindings(
				helix.ProjectNamedBinding("service", "name", "service"),
				helix.ProjectCurrentBinding("name", "workload"),
			),
	).
	Returning("routes")
```

```python Python
(
    read_batch()
    .var_as(
        "routes",
        g()
        .n_with_label("Service")
        .bind("service")
        .out("ROUTES_TO")
        .project_bindings(
            [
                BindingProjection.binding("service", "name", "service"),
                BindingProjection.current("name", "workload"),
            ]
        ),
    )
    .returning(["routes"])
)
```

Bindings are row-local, so each row pairs a workload with the service that reached it
rather than joining unrelated paths. After `bind`, end the traversal with
`projectBindings` or `projectDistinctBindings`: `valueMap`, `project`, `values`, `id`,
`label`, `edgeProperties`, `orderBy`, `repeat`, and `choose` are rejected with
`invalid_after_bind_operation`, and write batches cannot use `bind`. Cypher pattern variables, such as `s` in the
Cypher tab, stay bound for the whole row in the same way, so the statement needs no
`bind` step. Branches can bind optional values and coalesce
them during projection; see [Project correlated bindings](/database/helix-db/query-guides/projections#project-correlated-bindings).

## Branch traversals in Go

`sub()` starts a branch for `optional`, `union`, `coalesce`, `choose`, and `repeat`. Go's
`helix.Sub()` offers only `Out`, `In`, `Both`, `Where`, `Limit`, `Count`, and `Bind`.
For any other step, build the branch from a traversal's steps, as in
`helix.SubTraversalFromSteps(helix.G().OutE("WROTE").OutN().Steps())`.

## Avoid accidental path growth

- Filter as close to the source as possible.
- Use a label on relationship steps when the schema provides one.
- Add `dedup()` when multiple paths can reach the same entity.
- Bound recursive traversal with a maximum depth; see
  [Repeat a traversal](/database/helix-db/query-guides/advanced#repeat-a-traversal).
- Project only the fields needed by the caller.
