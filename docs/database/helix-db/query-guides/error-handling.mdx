Helix query failures expose a stable machine-readable code separately from the
human-readable diagnostic. Branch on the code; log or display the message.
Messages can gain context over time and are not a compatibility contract.

This page covers errors raised by the HelixDB engine in every run mode. A Helix Cloud
gateway can also return its own codes, such as `rate_limited` and `unauthorized`; see
[Helix Cloud gateway errors](/database/helix-cloud/operate/error-handling).

## TypeScript release compatibility

`@helix-db/helix-db` **3.1.0** exposes `HelixError.code`, `statusCode`,
`serverMessage`, `rawBody`, and explicit `retryable` metadata. The published
**3.0.4** package lacks these structured fields. Docker **v0.0.5** already
returns a confirmed transaction conflict as HTTP **409** with
`{"error":"transaction_conflict","msg":"<diagnostic>"}`.

Use both `error.code === "transaction_conflict"` and `error.statusCode === 409`
to recognize that condition. Reload the asset before rebuilding the mutation;
do not match diagnostic wording. A dropped connection after sending a write is
a `Network` failure with an unknown commit outcome, not proof that the write
was aborted. An explicit `writer_fenced_commit_outcome_unknown` response is also
distinct from a conflict and carries `retryable: false`. Reconcile state before
resubmitting such writes. The SDK does not automatically replay mutations.

This compatibility statement concerns transaction conflicts; it does not claim
that v0.0.5 implements every newer error classification in the reference below.

## HTTP error envelope

Every non-success response from `POST /v2/query` uses `error` for the static
code and `msg` for the readable message:

```json
{
  "error": "index_not_found",
  "msg": "planner error: missing text index for `Document.body`"
}
```

The response never adds a separate `code` field. A non-JSON response from an
older proxy or intermediary is still exposed by each SDK as readable details
with no code.

## Failure classes

Every code belongs to exactly one class, and the class alone sets the HTTP
status, the gRPC status, the `retryable` field and whether a failed write is
proven to have committed nothing. The [reference](#error-code-reference) lists
each code's status.

| Class | HTTP | gRPC | `retryable` | A failed write |
| --- | --- | --- | --- | --- |
| Invalid request | 400 | `INVALID_ARGUMENT` | absent | Committed nothing |
| Planning | 400 | `INVALID_ARGUMENT` | absent | Committed nothing |
| Not found | 404 | `NOT_FOUND` | absent | Committed nothing |
| Request timeout | 408 | `DEADLINE_EXCEEDED` | absent | May have committed |
| Transaction conflict | 409 | `ABORTED` | `true` | Committed nothing |
| Conflict with database state | 409 | `FAILED_PRECONDITION` | `false` | Committed nothing |
| Index backpressure | 429 | `RESOURCE_EXHAUSTED` | `true` | Committed nothing |
| Resource limit | 429 | `RESOURCE_EXHAUSTED` | absent | Committed nothing |
| Internal failure | 500 | `INTERNAL` | absent | May have committed |
| Unavailable | 503 | `FAILED_PRECONDITION` | absent | Committed nothing |
| Commit outcome unknown | 503 | `UNAVAILABLE` | `false` | May have committed |

HTTP 409 has two classes. `transaction_conflict` (`retryable: true`) can succeed
when resent unchanged. A conflict with the database's state, such as
`unique_constraint_violation` (`retryable: false`), fails again until that
state changes: choose another value or reconcile first.

## Cypher errors

`POST /v2/cypher` and `POST /v2/cypher/explain` report a failed statement with the
same `error` and `msg` fields and a `details` object:

```json
{
  "error": "resource_limit",
  "msg": "expression temporaries exceed the query memory budget",
  "details": { "detail": "memory_limit", "phase": "runtime", "span": null }
}
```

`error` is the category and `details.detail` the specific condition. Both are lower
snake case, like every code on this page. `details.phase` is `compile` (nothing ran)
or `runtime`, and `span` locates the failing statement text when it is known. A
failed statement commits nothing. gRPC carries the same JSON in the status details.
Embedded SDK errors join the three parts into one code,
`category:phase:detail`, such as `syntax_error:compile:undefined_variable`.

Request, storage, and transaction failures on the Cypher routes keep the native
envelope and the codes below.

| Category | Meaning | HTTP | Retry |
| --- | --- | --- | --- |
| `syntax_error` | The statement is not valid Cypher, for example `undefined_variable`, `unexpected_syntax`, or `invalid_parameter_use`. | 400 | After fixing the statement |
| `unsupported_feature` | Valid openCypher outside the supported profile, for example `merge`, `variable_length_pattern`, or `function` (an openCypher function this profile lacks; `msg` names it). | 400 | After rewriting the statement |
| `type_error` | A value has the wrong type for its use, for example `expected_node` or `invalid_property_type`. | 400 | After fixing the statement or data |
| `argument_error` | A function argument is invalid, for example `number_out_of_range`. | 400 | After fixing the argument |
| `arithmetic_error` | Arithmetic failed, for example `division_by_zero`. | 400 | After fixing the expression or data |
| `parameter_missing` | A referenced parameter was not supplied (`missing_parameter`). | 400 | After supplying it |
| `entity_not_found` | A statement read a node or relationship it had deleted (`deleted_entity_access`). | 400 | After fixing the statement |
| `constraint_verification_failed` | A plain `DELETE` targeted a node that still has relationships (`delete_connected_node`). | 400 | After using `DETACH DELETE` or removing the relationships |
| `resource_limit` | A per-query budget was exceeded, for example `memory_limit`, `result_limit`, `collection_limit`, or `expression_depth`. | 429 | Not unchanged; reduce the work. Distinct from the gateway's `rate_limited` |
| `access_mode_error` | A modifying statement reached a reader or a warm-only request (`writer_required`). | 503 | On the writer |
| `internal_planner_error` | The planner broke one of its own invariants. | 500 | No automatic retry |

The [Cypher guide](/database/helix-db/query-guides/cypher#what-is-not-supported) lists
the `details.detail` code for each construct outside the supported profile.

## Access the code in an SDK

<CodeGroup>

```rust Rust
match client.query::<serde_json::Value>(request).send().await {
    Err(error) if error.error_code() == Some("index_not_found") => {
        // Create the index, wait for it to become active, then retry.
    }
    Err(error) => return Err(error),
    Ok(response) => println!("{response}"),
}
```

```ts TypeScript
try {
  await client.query(request).send();
} catch (cause) {
  if (cause instanceof HelixError && cause.code === "index_not_found") {
    // Create the index, wait for it to become active, then retry.
  } else {
    throw cause;
  }
}
```

```go Go
if err := client.Exec(ctx, request, &response); err != nil {
	var helixErr *helix.HelixError
	if errors.As(err, &helixErr) && helixErr.Code == helix.QueryErrorCode("index_not_found") {
		// Create the index, wait for it to become active, then retry.
	} else {
		return err
	}
}
```

```python Python
try:
    response = client.query(request)
except HelixError as error:
    if error.code == "index_not_found":
        # Create the index, wait for it to become active, then retry.
        pass
    else:
        raise
```

```json JSON
{
  "error": "index_not_found",
  "msg": "planner error: missing text index for `Document.body`"
}
```

</CodeGroup>

Known Rust codes can also be parsed as `QueryErrorCode`. SDK wire fields remain
open strings so a newer server's unknown future code is preserved rather than
being collapsed or rejected.

## Other query boundaries

For gRPC, the status message remains human-readable and the same static code is
attached as ASCII metadata under `helix-error-code`. The gRPC status is the
code's [class](#failure-classes) status, so `unique_constraint_violation` is
`FAILED_PRECONDITION` and `index_backpressure` is `RESOURCE_EXHAUSTED`.

Embedded Rust errors expose `error_code()`. UniFFI errors carry two explicit
fields named `error` and `msg`; generated Python, Node, and Go bindings pass
that pair into their SDK error objects. Embedded callers never need to infer a
code from exception text.

## Stability and retry rules

- Existing code strings are frozen compatibility identifiers. New codes may be
  added, so applications must preserve and safely handle unknown values.
- A code describes the failure, not whether replaying a particular mutation is
  safe. Retry only idempotent work or work protected by an application-level
  idempotency key.
- `transaction_conflict` (HTTP 409, `retryable: true`) is normally retryable
  with bounded backoff. Other 409s conflict with the database's state and carry
  `retryable: false`; branch on the code, not the status alone.
- `index_backpressure` (HTTP 429) rejects the whole request before it takes
  effect and carries `retryable: true`. Retry it unchanged with bounded backoff;
  see [index backpressure](/database/helix-db/query-guides/search-consistency#index-backpressure).
- Availability and lifecycle failures should be retried only after the named
  condition changes. Validation and planning failures require a corrected
  request or schema/index configuration.
- `internal_*`, `storage_error`, and `response_serialization_error` are opaque
  by design. Retain the `msg` and server logs when escalating them.

### Active-text mutation limits

`active_text_mutation_limit_exceeded` reports a deterministic rejection before the
write transaction commits: one indexed text document is too large. The request's graph
changes are not committed. The error is caller-correctable and uses HTTP 400, gRPC
`InvalidArgument`, or the embedded `InvalidRequest` binding category. It is not a
transient rate limit or an unknown write outcome; retrying the identical mutation does
not resolve the limit.

For example, the HTTP query service returns:

```json
{
  "error": "active_text_mutation_limit_exceeded",
  "msg": "db error: Active text mutation exceeds output_operations: observed 20006, limit 16384. This is a hard per-document limit; shorten the indexed text."
}
```

Branch on `error`, not the wording in `msg`. The diagnostic identifies the resource,
the document's usage and its allowance. See [active-text admission limits](/database/helix-cloud/operate/limits#active-text-mutation-admission)
for the default allowances. The same engine policy applies to standalone databases;
embedded configurations may override it.

### Retryable conflicts

| Code | Meaning | HTTP | Retry | Correctable |
| --- | --- | --- | --- | --- |
| `transaction_conflict` | A concurrent transaction prevented commit. | 409 | Yes, bounded backoff | No request change required |
| `index_backpressure` | A vector or text index already retains its maximum unpublished work, so the whole write was rejected before commit, or a whole-index `strong` search's answer lies behind more than 800 committed but unpublished changes, or a `strong` text search would analyze more unpublished text in its partition than its bound allows (512 MiB of analysis by default), or a `strong` vector search would score more unpublished vector work than its bound allows (by default the index's retained-byte limit, which writes reach first). | 429 | Yes, bounded backoff | No request change required |
| `request_read_view_changed` | A standalone reader changed views during the request. | 409 | Yes, bounded retry | No request change required |
| `stale_index_generation` | A retained handle refers to a stale index generation. | 409 | Yes, reacquire state | No request change required |

## Migrate direct HTTP consumers

The field names changed while their roles stayed the same:

| Before | Now | Meaning |
| --- | --- | --- |
| `code` | `error` | Stable machine-readable code |
| `error` | `msg` | Human-readable diagnostic |

Old response:

```json
{
  "error": "planner error: missing text index for `Document.body`",
  "code": "index_not_found"
}
```

New response:

```json
{
  "error": "index_not_found",
  "msg": "planner error: missing text index for `Document.body`"
}
```

Current SDKs read both shapes during migration. Direct HTTP consumers must move
their code branch from `code` to `error` and their diagnostic read from `error`
to `msg`.
