<Update
  label="November 2026"
  rss={{
    title: "Docker v0.0.16 and CLI 3.7.0: bounded durable waits and faster bulk writes",
    description: "Durable requests stop waiting for storage after 30 seconds, bulk inserts run faster, index activation pauses less, and telemetry honors DO_NOT_TRACK"
  }}
>
- **Durable requests stop waiting for storage after 30 seconds.** A durable write waited for its WAL upload with no limit, so while the object store was unreachable, writes and native no-op requests hung. They now fail with `query_deadline_exceeded` (HTTP 408) after 30 s. The commit may still have happened, so reconcile before you resend. Index definition changes still wait without a limit.
- **Faster bulk inserts.** Each writer applies its commits on a thread of its own. An in-process bulk insert with 8 indexes and 8 clients went from about 10K to 16K–23K nodes per second, and its p50 from about 400 ms to 155 ms. At that rate writers reach the storage engine's L0 limit sooner, so p99 at 8 clients rose from about 0.5 s to 1.1–3.1 s.
- **Shorter pause when a secondary index activates.** The longest write gap during a 300K-row unique build went from 2.4 s to about 0.7 s, and during a 600K-row build from 11.9 s to 1.3 s.
- **Responses are serialized without copying the returned rows.**
- **Telemetry.** The server, the embedded runtime and the CLI turn telemetry off when `DO_NOT_TRACK` is set to anything but empty, `0`, `false` or `no`. `HELIX_TELEMETRY_LEVEL` also accepts `on`, `true`, `yes` and `1` for `basic`, and `false`, `no` and `0` for `off`. `basic` telemetry now carries pseudonymous project and deployment IDs and a per-session query count. See [`helix metrics`](/cli/command-reference/metrics) for what it sends.
- No storage changes since v0.0.15: upgrading needs no migration.
- **CLI 3.7.0** defaults to image v0.0.16, honors `DO_NOT_TRACK`, and passes its project ID, CI markers and `HELIX_DEPLOYMENT_ID` to the containers it starts. Projects that saved a `tag` in `helix.toml` keep using it until you change it.
</Update>

<Update
  label="November 2026"
  rss={{
    title: "Docker v0.0.15 and CLI 3.6.2: optional durability waits and non-blocking index builds",
    description: "await_durable false now skips the WAL wait, the WAL interval and SST codec are configurable, and index builds no longer stall reads"
  }}
>
- **Behavior change: `X-Helix-Await-Durable: false` now skips the durability wait.** Before, every write waited for its WAL upload whatever the header said. Writes stay durable by default: without the header, or with `true`, success still means the write is durable. With `false`, the server answers once the write is applied on the writer, so a crash before the next WAL upload loses it. Writes that send `true` also stopped flushing a second time, which had stalled writers under load: in one S3 test with 128 clients, they went from about 60 to 1,200 vector writes per second. See [execution headers](/database/helix-db/query-guides/http-api#execution-headers).
- **`HELIX_WAL_FLUSH_INTERVAL_MS`** sets the milliseconds between WAL uploads, from 1 to 60000 (default 100). A durable write waits for the next upload, so a lower value cuts write latency and costs more object-store PUTs.
- **`HELIX_SST_COMPRESSION`** chooses the codec of the storage files the server writes: `none` (the default) or `zstd`. Every file records its codec, so either setting reads both. Once `zstd` is on, v0.0.14 and earlier cannot read the data.
- **Index builds no longer stall reads.** Build steps fence only writers, and only activation pauses planning. During a 300K-row secondary build with 32 readers and 4 writers, reads went from 66K/s on average (8–11K/s for 15 s) to 205K/s, and writes from 350/s to 920/s. The build took 31.5 s instead of 23 s, because it now shares the machine with live traffic.
- **Duplicates are rejected while a unique index builds.** A write that duplicates a value the build already indexed fails with `unique_constraint_violation` (409). Before, the write was accepted and the build then blocked on it.
- **Conditional updates keyed by a unique property read one row.** A filter that combines a unique equality with other conditions now looks up the unique value and filters it, instead of intersecting every index involved. Five guarded claims over 1M jobs went from about 34 s to 35 ms.
- **Write-path fixes.** A large index publication no longer freezes the server for about 1.6 s, and very large merged index-queue rows no longer get the server killed for running out of memory under sustained vector writes. A `SET` on a node no longer aborts concurrent edge inserts on it. Node deletes read and flush per batch: `DETACH DELETE` of 6,000 connected nodes went from about 1.0 s to 0.5 s. Cypher `CREATE` and `SET` batch their storage work across rows.
- **Faster vector publication.** Worker threads score the publisher's HNSW search distances, so the index worker publishes 1.4–1.8 times as many vectors per second.
- **Upgrading.** New storage files index rows of 1 MiB or more by their full key. Older and newer images read both forms, and nothing is rewritten. Encodings, merge operators and the WAL format are unchanged.
- **CLI 3.6.2** defaults to image v0.0.15.
</Update>

<Update
  label="November 2026"
  rss={{
    title: "Docker v0.0.14 and CLI 3.6.1: concurrent request throughput",
    description: "The planning catalog is reused until it changes, so concurrent requests no longer queue behind one another"
  }}
>
- **Concurrent requests no longer queue on the planner.** Every request rebuilt its planning catalog, one request at a time per scope, which capped a scope at about 2,500 requests per second however many clients there were. The catalog is now reused until an index change replaces it, and the writer reads through a snapshot. On in-memory storage with 8 secondary indexes, reads at 128 clients went from about 2.6K to 646K per second, writes at 32 clients from 2.2K to 13K, and a 90/10 mix at 128 clients from 2.2K to 87K. Single-client writes are unchanged.
- **A dropped index finishes dropping** when its client disconnects, and a drop that races a build step retries instead of failing with `transaction_conflict`.
- No storage changes since v0.0.13.
- **CLI 3.6.1** defaults to image v0.0.14.
</Update>

<Update
  label="November 2026"
  rss={{
    title: "Docker v0.0.13 and CLI 3.6.0: SQL, diagnostics, and one status per error code",
    description: "SQL queries, helix doctor, breaking changes to empty returns and error statuses, fsync on local disk, and index builds that finish under writes"
  }}
>
- **Breaking: an empty single-row return is `[]`, not `null`.** An entry the planner proved returns at most one row, such as a one-ID source, `limit(1)` or a search with `k` of 1, returned `null` when it matched nothing. Every row return is now an array, so test for an empty array instead of `null`. `count()` and `exists()` keep their scalar values. See [the query walkthrough](/database/helix-db/core-concepts/overview).
- **Breaking: each error code has one HTTP status.** The code alone now sets the HTTP status, gRPC status and `retryable` hint. A duplicate unique value now returns `409` instead of `500`, `node_not_found` and the other not-found codes `404`, `query_deadline_exceeded` `408`, `query_memory_limit_exceeded` `429`, and several invalid-input codes `400`. A writer-only request sent to a reader returns `writer_mode_required`. Clients that branch on status codes should branch on the error code. See [failure classes](/database/helix-db/query-guides/error-handling#failure-classes).
- **Breaking for Cypher clients: Cypher error codes are lower snake case**, like every other code: `resource_limit` and `memory_limit` instead of `ResourceLimit` and `MemoryLimit`.
- **[SQL](/database/helix-db/query-guides/sql).** `POST /v2/sql` and `POST /v2/sql/explain` translate one SQL statement into Cypher and run it on the same planner. gRPC and embedded databases serve SQL too.
- **[`helix doctor`](/cli/command-reference/doctor) and `GET /v2/diagnostics`** check a server's storage, S3 bucket region, disk cache, memory, index publication, and recent queries' index use.
- **Local disk storage fsyncs every write.** With `HELIX_DATA_DIR`, a write acknowledged as durable could still sit in the page cache, so a crash or a full host disk could leave a database that would not open. Each storage file is now synced before it is published. Durable write throughput was unchanged in testing. Disk storage also deletes old manifest and compaction files again; they had stopped being collected.
- **Secondary index builds finish under sustained writes.** A build could stay in catch-up for as long as writes kept arriving, so equality lookups kept scanning their label and each write batch got slower. In one test, batches that grew from 1.7 s to 52 s now level off at about 100 ms once the build finishes.
- **Faster writes to large rows and edges.** Writes to a busy label, a hub node or a low-cardinality equality value no longer read the stored row they merge into, and a request that adds edges node by node no longer flushes pending index work before each node read. Typed Cypher relationship patterns start from relationship-label bitmaps.
- **Embedded readers reopened on the same disk root stop leaking file descriptors**, and a writer and its readers share one disk cache.
- HelixDB's encodings, merge operators and WAL format are unchanged.
- **CLI 3.6.0** defaults to image v0.0.13 and adds `helix doctor`. `helix auth login` supports every sign-in method.
- SDK methods for Cypher and SQL are in the repository but not yet in a published SDK release; send direct HTTP requests until then.
</Update>

<Update
  label="October 2026"
  rss={{
    title: "Docker v0.0.11 and CLI 3.4.4: faster, bounded index queues",
    description: "Strong searches decode pending index work once per request, strong text search keeps working during ingest, writers reopen faster, and queue admission tracks real memory"
  }}
>
- **Strong text search keeps working during ingest.** A `strong` text search now has its own bound, 512 MiB of unpublished text per partition by default (it was one publication's 64 MiB), and reuses analyses of pending text across searches. Ingest bursts of 20K–40K documents that made v0.0.10's strong text searches fail with `index_backpressure` now complete with no rejections, and a strong text search behind 5,000 pending documents dropped from about 200 ms to 30 ms. Set `HELIX_STRONG_TEXT_SEARCH_MAX_ANALYSIS_BYTES` to change the bound; past it the search fails with retryable `index_backpressure` (`pending_text_analysis_bytes`).
- **Strong searches decode pending index work once per request.** Several searches in one request share one decoded copy of the pending queue, decoding and exact scoring run off the async workers so they no longer stall other requests, and four strong vector searches in one request behind 160K pending 768-dimension changes went from about 5.0 s to 2.2 s.
- **Strong vector searches are bounded.** A `strong` vector search decodes and scores at most the index's retained-byte limit of unpublished work by default (1 GB, so writes reach backpressure first). Set `HELIX_STRONG_VECTOR_SEARCH_MAX_PENDING_BYTES` to lower it; past it the search fails with retryable `index_backpressure` (`pending_vector_bytes`).
- **Queue admission tracks real memory.** Each queued index operation now counts its encoded size plus 576 bytes against the 1 GB per-index limit, so a backlog of many small operations, such as deletes, can no longer use several times the limit in memory. Such backlogs reach `index_backpressure` sooner; the 250,000 pending-entity limit is unchanged.
- **Writers reopen faster with a large backlog.** Opening a writer loads its queued index work one queue at a time instead of decoding every queue at once: a 2.26 GB backlog opened in about 5 s instead of 25 s, with peak memory bounded by the largest queue instead of the whole backlog.
- **Publication drains in linear time.** Selecting work to publish no longer rescans the whole queue each time, which was 9.4 s of bookkeeping per 250K-operation drain and is now 0.16 s, and a queue retired by an index drop is discarded without being re-read.
- No storage changes since v0.0.10: upgrading from v0.0.10 needs no migration. Upgrading from v0.0.9 or earlier follows the v0.0.10 notes below.
- **CLI 3.4.4** defaults to image v0.0.11. Projects that saved a `tag` in `helix.toml` keep using it until you change it.
</Update>

<Update
  label="October 2026"
  rss={{
    title: "Docker v0.0.10 and CLI 3.4.3: asynchronous vector and text indexing",
    description: "Vector and text index work moves off the write path, searches choose strong or eventual consistency, and counts over range indexes with other filters are fixed"
  }}
>
- **Upgrading: index storage version 5.** The first time a v0.0.10 writer opens a database, it upgrades the index storage version from 4 to 5. It rewrites only the version marker and rebuilds no index. After that, v0.0.9 and earlier refuse to open the database with `unsupported_index_storage_version`:
  - Upgrade readers before the writer; v0.0.10 readers serve both versions.
  - Never start a v0.0.9-or-earlier writer against an upgraded database.
  - Take a backup before upgrading if you may need to roll back.
- **[Vector and text indexes publish asynchronously](/database/helix-db/query-guides/search-consistency).** A write commits its graph change together with a durable queued index operation, and a background index worker publishes it into the vector or text index, so writes no longer wait on index maintenance. Steady vector insert publication went from 6.2 to 239 per second. Index builds no longer livelock under concurrent writes: on a c7i.8xlarge with 100 writes/s during the build, backfilling 100K 768-dimension vectors on disk finished in about 2,500 s, where v0.0.9 never finished.
- **Search consistency.** Read requests set `search_consistency` to `strong` (the default) or `eventual`. `strong` searches include every committed write, published or not. `eventual` searches include a bounded amount of unpublished work and serve the rest as last published, so they can return a node or edge that has since changed tenant, label or indexed property. Write requests always search `strong`, and a write batch that searches an index fails with a retryable `transaction_conflict` if the index worker publishes into that index first. The SDK options ship in the next SDK releases; until then, send `search_consistency` in a direct HTTP request.
- **[Index backpressure](/database/helix-db/query-guides/search-consistency#index-backpressure).** Each index retains at most 1,000,000,000 bytes or 250,000 pending entities of unpublished work. Three cases fail with `index_backpressure` (HTTP 429, `retryable: true`) before the request takes effect: a write past either limit, a whole-index `strong` search behind more than 800 unpublished changes, and a `strong` text search that would analyze more unpublished text than one publication may (64 MiB by default). Retry it unchanged with bounded backoff. A single write that stages more than 8 MiB of index work for one index fails with `index_operation_batch_too_large` (HTTP 400); split it.
- **[Text write limits are per document](/database/helix-cloud/operate/limits#active-text-mutation-admission).** `active_text_mutation_limit_exceeded` now checks each indexed document against its own allowances, about 16,000 unique terms, instead of limiting a write to 512 text-indexed entities.
- **A failing index entry no longer stalls its index.** An entry whose index update fails the same way every time, for example on damaged index data, is held back while the rest of the index keeps publishing. `GET /healthz` counts it under `blocked_index_entity_count`, the server logs an error naming it, and the worker retries it about once a minute. See [troubleshooting](/database/helix-db/query-guides/troubleshooting).
- **Fixed: `missing simhash` after re-embedding and then deleting a node** (the v0.0.9 known issue). Re-embedding a node no longer loses track of the vector index (HNSW) links that point at it, so deleting it later removes them all, and a node is never linked to itself. Indexes written by v0.0.9 and earlier can still hold such links; drop and recreate the vector index to repair them.
- **Fixed: counts over a range index with other indexed filters.** A `.count()` over `N<L>.where(...)` or `E<L>.where(...)` that combined a range condition with other indexed conditions counted the range alone, for example 149 rows instead of 49. Counts now apply every filter.
- **CLI 3.4.3** defaults to image v0.0.10. Projects that saved a `tag` in `helix.toml` keep using it until you change it.
</Update>

<Update
  label="October 2026"
  rss={{
    title: "Docker v0.0.9 and CLI 3.4.2: an always-on S3 disk cache and faster cold vector search",
    description: "S3 storage always caches on local disk, first vector searches after a restart are much faster, and source filters and counts always use indexes"
  }}
>
- **Upgrading S3 deployments** — S3 storage now always writes a local disk cache, so an S3 container that ran v0.0.8 or earlier can fail or use more resources after the upgrade:
  - The cache directory, `/var/cache/helix` unless `HELIX_DISK_CACHE_DIR` names another, must be writable. Mount a volume there (required with a read-only root filesystem), and set `HELIX_DISK_CACHE_DIR` when running as a user other than `65532`.
  - The hard open-file limit must be at least 26,600 at the default budget (about 8,200 or fewer at 1 GiB or less). Raise it with `--ulimit nofile=65536:65536`.
  - RSS grows by the block cache's index, about 20–70 MiB at the default budget and twice that briefly after a restart.
  - Without `HELIX_DISK_CACHE_BYTES`, the 8 GiB default budget must fit the cache's filesystem, or startup fails.
- **[S3 always uses a local disk cache](/database/helix-db/start-here/local-development/local-server#add-a-local-disk-cache)** in `/var/cache/helix` by default, with an 8 GiB default budget. Memory-only S3 is gone: once a vector index outgrew the memory cache, every graph hop waited on its own S3 request. `HELIX_DATA_DIR` and in-memory storage are unchanged.
- **Faster first vector searches on S3.** Cold batch reads overlap their block fetches, expansions read parents concurrently, and projections prefetch the records they need. After open, the server also warms vector search rows into the disk cache in the background; readiness never waits for it. `HELIX_DISK_CACHE_WARM=off` (default `on`) turns startup warming off. On 2 CPUs, 4 GiB of memory and an 8 GiB cache over S3, the first global vector top-50 after open went from 30.8 s on v0.0.7 to 714 ms once the ~26 s warm finished.
- **Index sets are kept across `ForEach` iterations and unrelated writes** in the same request, which removes the v0.0.8 known limitation. A set is read again only when an iteration binds a parameter it depends on, or a write creates, deletes or changes indexed properties of nodes with its label. A batch that expands, filters on an index and adds an edge per iteration runs about twice as fast.
- **Source filters and counts always use indexes.** `N<L>.where(...)`, `E<L>.where(...)` and counts on indexed properties no longer scan the label, including partly indexed ORs, long `IN` lists, parameter lists, `== null`, and counts over `.as()` / `.store()`. A label scan only happens when no condition has an index. On 50k rows, counts after `.as()` went from up to 1.1 s to under 5 ms, and 200-value `IN` lists from up to 1.5 s to about 0.2 s.
- **Upgrading** — the stored data format is unchanged. Databases written by v0.0.8 open directly with v0.0.9.
- **Known issue** — updating a node's vector (re-embedding it) and later deleting that node can leave vector index (HNSW) links pointing at the deleted node, and searches that reach them fail with `missing simhash`. Earlier releases are affected too, and a fix is in progress. To repair an affected index, drop and recreate the vector index.
- **CLI 3.4.2** defaults to image v0.0.9. With `--disk` or S3 storage, `helix start` mounts a per-instance `helix-<project>-<instance>-cache` volume at `/var/cache/helix` for the disk cache, with a 64 MiB budget in disk mode and 1 GiB for an S3 bucket. `helix stop` keeps it and `helix prune` removes it.
</Update>

<Update
  label="September 2026"
  rss={{
    title: "Docker v0.0.8 and CLI 3.4.1: indexed filters after traversals",
    description: "Filters after an expansion always use their indexes, and multi-index filters read them concurrently"
  }}
>
- **Filters after a traversal always use indexes.** A `.where(...)` on indexed properties after `.out()`, `.in()` or another expansion is answered from the index, including in counts, limits, `exists` checks and branch or union bodies, instead of reading records one by one. - **Known limitation** — inside `ForEach` bodies (`forEachParam` / `for_each_param`), and after a write in the same request, index sets are re-read once per iteration or write. An improvement is in progress.
- **Upgrading** — the stored data format is unchanged. Databases written by v0.0.7 open directly with v0.0.8.
- **CLI 3.4.1** defaults to image v0.0.8.
</Update>
