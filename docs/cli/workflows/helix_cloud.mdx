Use the CLI to sign in to Helix Cloud, link a project to a Cloud database, and run
queries against it. You need a Helix Cloud account and at least one database; see
[Get started with Helix Cloud](/database/helix-cloud/start-here/using-the-cloud), or
[move a local project to Helix Cloud](#move-a-local-project-to-helix-cloud) to create one from the CLI.

<Steps>
  <Step title="Authenticate with WorkOS">
    ```bash
    helix auth login
    helix auth status
    ```

    Login needs an interactive terminal. On a remote machine over SSH, see
    [Log in over SSH](/cli/command-reference/auth#log-in-over-ssh).
  </Step>
  <Step title="Link a project and database">
    ```bash
    helix init cloud
    ```

    The CLI picks your workspace, project, and database: it uses the only one of each or
    asks you to choose. It writes the project and a `production` database link to
    `helix.toml`. To link another database later, run `helix add cloud --name <name>`.
  </Step>
  <Step title="Run a query through the broker">
    ```bash
    helix query production -e 'readBatch().varAs("c", g().nWithLabel("User").count()).returning(["c"])'
    helix shell production
    ```

    `helix init cloud` writes no example request. `-e` needs Node.js 20+ and npm; to send JSON
    instead, write a request file as described in
    [Request shape](/cli/command-reference/query#request-shape) and pass it with `--file`.
  </Step>
  <Step title="Inspect the linked resources">
    ```bash
    helix status
    helix database
    helix logs production
    ```

    Inside a linked project, Cloud commands default to its project and databases, so
    they need no IDs.
  </Step>
</Steps>

Pass a resource by ID, slug, or name when you want a different one, for example
`helix database list --project <project>` or `helix query tenant:<id> --file request.json`. Flags
go after the subcommand. In scripts, add `--json` for machine-readable output; commands then never
prompt. See [Cloud resource resolution](/cli/command-reference#cloud-resource-resolution).

## Move a local project to Helix Cloud

Starting from a project created with `helix init local`:

<Steps>
  <Step title="Create and link a Cloud project">
    ```bash
    helix auth login
    helix project create "My App" --link
    ```

    `--link` writes `[project] id` and `workspace_id` to this directory's `helix.toml` and keeps the
    local instances. To use an existing Cloud project instead, run `helix project link <project>`.
  </Step>
  <Step title="Create a database">
    ```bash
    helix database create orders --plan <plan-code>
    ```

    This creates a tenant database in the linked project and prints its default read-write
    application key once on stdout; store it in a secrets manager for your application. The CLI
    requires `--plan` for a shared database and prompts for it in a terminal; list the plan codes with
    `helix api get /v1/workspace-plans`. Pass `--cluster <cluster>` instead to create the database on
    a dedicated cluster.
  </Step>
  <Step title="Add it to helix.toml">
    ```bash
    helix add cloud --name production --database orders
    ```

    This writes an `[enterprise.production]` table with the database's `tenant:<id>` target.
  </Step>
  <Step title="Query it">
    ```bash
    helix query production --file examples/request.json
    ```

    The Cloud database starts empty. The CLI does not copy local data, so replay your write requests
    against `production`.
  </Step>
  <Step title="Connect your application">
    Applications reach the database through its gateway with an application key, not through the
    CLI's session. `helix database get orders --json` prints the gateway host as
    `connectionEndpoint`. Create more keys with `helix database key create --access read-only` or
    `read-write`. See [Connect to Helix Cloud](/database/helix-cloud/start-here/working-with-enterprise)
    and [HTTP API authentication](/database/helix-db/query-guides/http-api#authentication).
  </Step>
</Steps>

## How Cloud queries are authorized

- `helix auth login` creates a WorkOS session that identifies you, using GitHub, Google,
  Microsoft, single sign-on, or an email and password. The CLI never uses database API keys.
- Cloud queries go through the Helix Cloud backend (the broker), not directly to the
  database gateway. The broker forwards each authorized request with its own gateway
  credentials, which the CLI never receives.
- Reads require the `database.query.read` permission and writes require
  `database.query.write`. Both are granted per project, on the project that owns the database.
  Project-management access does not imply query access.
- Owners and admins have both query permissions by default. Members have neither unless
  explicitly granted.
- Local queries are unaffected and run without authentication.

## Keys and credentials are not logins

- `helix database key` creates application keys for your own services that call the
  gateway directly.
- `helix service-credential` manages credentials for headless agents on the MCP endpoint.
  MCP tool access follows the credential's project grants, and these sessions do not
  get Cloud discovery or observability tools.

Neither can be used to sign in to the CLI, so the CLI's Cloud commands do not run unattended. See
[Run in CI](/cli/scripting#run-in-ci) for what a CI job can use instead.
